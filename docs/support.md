# What tls-forge reproduces, and how far that is checked

A request that "looks like Chrome" is a claim about many separate things: the
TLS handshake, the HTTP/2 connection preamble, the order and values of every
header, what happens on a redirect, which requests go out at all, and the
TCP/IP packets underneath. This page says, for each of them, whether tls-forge
reproduces the browser, how that is checked, and where it is known not to.
Only what is marked **checked** is promised.

Draft of 2026-10-16. The shipped profiles are `chrome_151` to `chrome_155`,
each captured on macOS, Linux and Windows; the measurements behind this page
were taken with Google Chrome 155.0.8059 on macOS, against local servers.

## How a behaviour becomes "checked"

1. It is measured from a real Chrome build, against a local server that records
   what arrived byte for byte (`tls-forge serve`, `tls-forge capture`).
2. The measurement is kept, either in a profile under `profile/data/` or as a
   fixture under `testdata/`.
3. A test holds tls-forge's own output to it, and `tls-forge compare` reports
   any difference against the browser installed on the machine it runs on.

A behaviour that has not been through these steps is not claimed, however
plausible it looks.

The five fixtures of what a page does, `testdata/chrome155-requests.json`,
`testdata/chrome155-connections.json`, `testdata/chrome155-hpack.json`,
`testdata/chrome155-decoding.json` and `testdata/chrome155-flow.json`, were
measured on the bench in `internal/harness`: a server that keeps every request
as the bytes said it, its header block as the client wrote it into HPACK, and
the connection it came on, over HTTP/2, over HTTP/1.1 alone and over plain
HTTP, each scenario's page and script, and each page whose decoding is asked
about; and one that sends an answer in the parts a scenario names and keeps
every WINDOW_UPDATE the browser sends while it reads it. It measures a browser
again, and writes the fixtures, or with `--check` holds the browser to them:

```bash
go run ./internal/harness/measure --browser "/path/to/Google Chrome" --check
```

Google Chrome 155.0.8059.80 on macOS, measured again on 2026-10-17, is what
the fixtures of requests and decodings say, scenario for scenario and page for
page, and measured twice that day, and again on 2026-10-18 with the scenarios
added then, what the fixture of connections says, as it is what the fixture of
header blocks says, measured twice on 2026-10-18, and what the fixture of
window updates says, measured twice that day. A
release holds its reference build to the fixtures of requests and decodings
the same way ([pinned](pinned.md)).

## Platforms

The shipped profiles cover macOS, Linux and Windows. A version named without a
platform, such as `chrome_155`, is this machine's capture; on a machine none of
the three describes, it is another platform's, and the run header says so.
Android and iOS browsers, Firefox and Safari can be measured with
`tls-forge capture --manual`; nothing about them ships.

The measurements behind the rows above were taken on macOS, and every test
that sends a measured scenario through tls-forge (requests and their
connections, HPACK, HTTP/1.1 records, ALPS, WINDOW_UPDATEs, URLs, False Start,
the first request's frames, the ClientHello) sends it wearing
`chrome_155_linux` and `chrome_155_windows` as well as `chrome_155_macos`.
What Chrome's network stack does, the same code on every platform, is held to
the measurement; what the platform decides, `sec-ch-ua-platform` and the
client hints a server asks for, is held to the profile's own values, written
as Chrome writes them: HPACK codes a value shorter when it can, so `"Windows"`
goes Huffman-coded and `"macOS"` does not, and an HTTP/1.1 request's head is
as long as the profile's values make it, which decides whether a body goes in
the head's write, as it does when the two are no more than 1,400 bytes. Each
profile's own ClientHello, captured on its platform, is alike the one measured
on macOS under every rule `compare` has, and the hellos tls-forge sends
wearing it, cold and resumed, are held to the macOS measurements. Each
profile's client hints are what Chrome on its platform sent a page that asked
for every one: macOS's measured on a Mac, Linux's and Windows's on GitHub's
runners (`capture.yml`). Left out, and said so by the tests and the check: on
Windows a 401 offering Negotiate or NTLM, which Chrome there answers through
SSPI and tls-forge does not. Chrome itself on Linux and Windows is measured
against the same fixtures by the weekly drift check
(`.github/workflows/drift.yml`).

## Checking a machine of your own

```bash
tls-forge compare
```

measures the Chrome installed here and the selected profile against the same
local server, and prints every difference it finds, after what it measured:
the browser's build, platform and mode, and the requests compared. A run with
no differences says so; the rows above marked "differs" or "not modelled" are
not part of what it compares, and `--json` carries the rule each field was
compared by.
