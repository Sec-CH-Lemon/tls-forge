# A8/C03: GREASE SETTINGS на каждое соединение

> Промежуточный отчёт этапа; итоговая приёмка и ограничения: [A8](A8.ru.md).

Механизм и JSON исправлены; нативная приёмка Chrome156 остаётся отдельным
обязательным условием A8. Engine остаётся неопубликованным1.0.0.

Chrome156.0.8078.74 закрепляет quiche a1628192cf32ba40d21e0dd80f485d68c24ff87a.
QuicSendControlStream::MaybeSendSettingsFrame получает uint32 N из RandBytes,
вычисляет ID31*N+33 и отдельно получает uint32 value. Флаг
quic_enable_http3_grease_randomness по умолчаниюtrue. Источники и их хеши
сохранены: [checks-a8-grease.json](checks-a8-grease.json).

До: JSON задавал N=1e9..9999999999, nonzero=true, tls-client рисовал значение
на транспорт. Замороженное дерево до исправления, один продуктовый Client,
64 холодных соединения: все64 попали в один бин, statistic960.000. Это
реальный wire RED, не вывод из отсутствия новой API. Более ранние отказы
тестового стенда сохранены и в это доказательство не засчитаны.

После: 15 JSON задают N=0..4294967295, nonzero=false. Исторические builds
явно наследуют выбор по источнику156; это не новый замер старых браузеров.
Общая фабрика quic.Transport создаёт копии настроек ровно на соединение
для обычного/early/direct пути. tls-client передаёт правила и снимок основы,
не выбирая их по имени браузера. Соединение сохраняет SETTINGS при reuse.

Публичный путь JSON→Load→Client.Do проверен на независимом raw H3 peer.
Крайние N=0/4294967295 и фиксированные повторения допустимы. Для cold cohort
используется WithoutSessionResumption и CloseIdleConnections с сохранением
транспорта; JSON ожидания QUIC отделяет опыт от выигрыша готового TCP-сокета.
Обычная политика выбора протокола не изменена. Три race-прогона по64 соединения
приняты. Заранее заданный smoke-критерий:16 равных uint32 бинов, Pearson≤60;
это контроль грубого замораживания/диапазона, не доказательство качества RNG.
Отдельный прогон хранит исходные пары SETTINGS всех64 соединений.

Три race-прогона новых fork regressions прошли. Оба полных QUIC gate приняты:
2562 test runs на каждом графе, со старым именованным долгом, без новых отказов.
Полные tls-client gates и окончательные хеши отражены в manifest. Перечень
F09stage2 не ослаблен. profile suite PASS8.464s, targeted lint0issues.

Нативный Chrome156 cohort, распределение браузера, Linux/Windows QPACK и
полный root QA ещё не завершены. Совпадение генератора по исходнику и
продуктовые регрессии не закрывают эти условия и не доказывают неотличимость.


## Lower-boundary placement correction

Закреплённый HttpEncoder::SerializeSettingsFrame сортирует все пары по ID.
Реальный принудительный N=0 воспроизвёл ошибку:33 шёл после51. Новый
`h3.grease_setting_placement` выбирает `last` либо `before-greater-id`;
статический вектор остаётся в объявленном порядке. Текущие15 Chrome-профилей
выбирают before-greater-id, совместимые legacy/catalogue JSON сохраняют last.
Для151–154 это явное наследование156, не новый замер их старых сборок.

Новый выбор обязателен на executable boundary. Общий registry проверяет тип/
значение, так что Inspect/Save/Clone старого архива не добавляют выбор; явная
Migrate создаёт отдельного кандидата. Все изменения остаются в едином ещё
неопубликованном engine1.0.0. В профилях не появился выполняемый код.

Оба JSON-варианта, N=0/max, reuse/redial и подмена имени/UA проверены через
Client.Do; неправильный/отсутствующий выбор отвергается до транспорта. Три
race-повтора PASS11.825s, пакет profile PASS9.048s100% в опубликованном графе.
Регаты utls/tls-client standalone+production и quic/fhttp production приняты
без новых исключений; их известный долг109 не закрыт и не расширен.

Исходник SerializeGreasingFrame также подтвердил классификацию payload как
случайных байтов: uint32N, длина=Nmod4, отдельный RandBytes payload. Оригиналы
сохранены. Анализатор теперь проверяет полное размещение generated setting и
отвергает производный отрицательный контроль N=0-after51. Положительная
нативная выборка до исправления сохранена отдельно; новая приёмка продолжается.
