## S03: PSK + HelloRetryRequest

utls `281f37fda04188b3fe886fd58c09ddcdec13c8fe` пересчитывает binder после
сериализации настоящего профильного ClientHello2, с транскриптом
message_hash(CH1)||HRR||Truncate(CH2). Данные браузера не менялись. Очищается
cached length PSK при его снятии из-за несовместимого hash. Неизвестная opaque
PSK implementation получает явный отказ вместо неподходящего binder.
Настоящий ECH `helloRetrySpecECH` остаётся отдельным неизменённым путём.

На одних native crypto/tls peers (P-256/P-384-only и X25519 control) выполнены
три шестизапросные серии на каждый вариант. До исправления: 18 отказов из54,
15 сервером подтверждённых resumption. После: 54/54 успешны, 45 resumption.
Root regression проверяет шесть новых соединений на каждом curve и требует
DidResume на2–6; простой успех полного handshake его не удовлетворяет.
Тот же контроль добавлен в сам utls. Полный utls suite и целевые race-тесты
проходят, в том числе pinned `GOWORK=off` в основном модуле.

Chrome156.0.8078.48/macOS arm64: девять независимых headed/minimized контекстов,
54 запроса, 36 resumption. В этой первой кампании запрос2 ещё полный,3–6
возобновляются. Финальный повтор показал вариативность запроса2. Прежняя
интерпретация через NIK не доказана; причина времени готовности кэша отдельно
не измерялась. Сравнение CH2 проводится по фактическому cold/resumed состоянию,
не по порядковому номеру запроса; общий lifecycle/NIK не объявлен совпавшим.

36 Chrome и36 candidate HRR: совпали полный статический состав и векторы CH2,
правило сохранения extension order/random/session ID/GREASE ECH внутри пары,
замена key_share и пересчёт PSK. Между соединениями extension order перемешан;
сравнивается multiset с сохранением данных. GREASE codepoint нормализуется
точечно в cipher/group/version/signature_algorithm/extension векторах.
Исходный comparator failure до учёта signature GREASE сохранён; mutation
обычного signature algorithm отвергается. Это не проверка распределения RNG.

Независимый Python HMAC/HKDF oracle вычисляет binder по оригинальным
CH1/HRR/CH2 и server-issued secret. Все binders корректны; отдельно ломаются
CH1, HRR, CH2 и отсутствие message_hash. Проверены также actual peer
DidResume и полный raw-handshake multiset: исходные bytes всех504 сообщений
из pcap совпадают с socket transcripts. Повторяющиеся ключи JSON tshark сохраняются; обычный
last-key-wins разбор терял144 сообщения и был отвергнут. HTTP расшифрован
непосредственно из исходного pcap с отдельным keylog. Original pcap не менялся,
потерь tcpdump —0; TLS secrets остаются только в ignored captures.

## S06

S06 реализован отдельными коммитами utls:

- `d889bc3` — настоящий ECH запрещает TLS1.2 False Start; отказ принимается
  только после аутентификации Finished. Held/corrupt-Finished контроль красный
  до исправления и зелёный после. Обычный TLS1.2 и GREASE сохраняют False Start.
- `e2b817b` — сертификат проверяется на точную длину, включая extra output после
  валидного Certificate. Уже существующий hard ceiling сообщения262144 байт
  применяется до decoder/allocation; читается не более declared+1. Zstd имеет
  один worker и ту же memory/window границу. Все три кодека проверены. На
  declared16MiB: до16 828 320 байт выделений, после около4688 байт. Подпроцесс
  ограничен временем и памятью. Encrypted UConn peer подтверждает bad_certificate
  для extra output и профильный decode_error50 для повреждённого кодека.
- `54dd25b` — обязательная пустота handshake buffer перед всеми read-key
  transitions, включая KeyUpdate, и перед HRR у сервера. Write keys меняются
  первыми, чтобы alert защищался правильными ключами. Проверены native и
  профильный UConn, trailing server/client messages и double-ClientHello.
- `225cded` — cached chains перепроверяются по актуальным корням и времени
  перед client/mTLS-server resumption в TLS1.2 и1.3. Неподходящий клиентский
  cache entry удаляется; следующий handshake полный и вновь проверяет доверие.
  Матрица охватывает RootCAs, GetConfigForClient/ClientCAs, истечение корня,
  профильный UConn и возврат к корректному resumption после восстановления CA.

Подтверждены первичные записи Go:
[CVE-2025-61730 / GO-2026-4340](https://pkg.go.dev/vuln/GO-2026-4340) и
[CVE-2025-68121 / GO-2026-4337](https://pkg.go.dev/vuln/GO-2026-4337).
Код и регрессии сверены с установленным Go1.26.10; web-доступ к страницам CL
был недоступен. Перенесены соответствующие guards и chain helper, с сохранением
существующих явных insecure-time/name API параметров. Это проверка двух
согласованных исправлений, не обзор всех изменений/CVE crypto/tls.

Профильные JSON/legacy templates и engine/version.json не менялись. Новые
переключатели не нужны: речь об integrity/cryptography и hard resource bounds.
Существующий `tls.certificate_decode_alert` продолжает приходить из JSON.
Настоящий ECH retry builder не менялся. Full utls suite с race проходит,
включая исходные ClientHello/record replay fixtures. Одному старому positive
ECH-fixture добавлен его же тестовый RootCAs во второй Config; проверки outer/
inner PSK сохранены полностью. Первый wire-test fixture без OmitEmptyPsk и
промежуточная build diagnostic с отсутствующим x509 import сохранены отдельно.

headed/minimized контекстов и54 production Client.Do запроса на тех же peers.

37 resumption; вариативный второй запрос не превращён в константу профиля.
