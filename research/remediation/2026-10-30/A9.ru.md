## Что изменилось

По умолчанию все воркеры одной личности — одного proxy URL либо direct —
используют общий `Client` и его существующие пулы сайтов. Запрос, retry и
снимок pcap больше не закрывают этот общий пул; его закрывает запуск CLI.
Разные proxy URL сохраняют отдельные клиенты, cookies и TLS sessions.
Серверное закрытие, idle/lifetime/eviction policy по-прежнему могут потребовать
новое соединение. Библиотека, профильные JSON, SDK и четыре форка не менялись.

`--fresh-connection` восстанавливает прежние клиенты воркеров и освобождение
idle-соединений после каждой попытки. `--reuse-connection` сохраняет отдельный
клиент на строку входного списка. Флаги взаимно исключаются. Существующее
поведение `--retry-as-browser` сохраняется и в этих режимах.

Lookup, probe `/cdn-cgi/trace` и разрешение proxy hash теперь требуют
`--exit-lookup`. Probe/resolve дополнительно требуют отчёта либо `--output`.
`--no-exit-lookup` явно оставляет новый default; значение `false` само по себе
ничего не включает. Два положительных флага вместе отклоняются до сети.
Пассивные CONNECT/response metadata и настроенные CONNECT `ask` поля остаются.
При выключенном lookup терминал/JSON/log/trace сохраняют причину
`not requested (enable with --exit-lookup)`, HTML прямо сообщает, что запрос
определения адреса не делался. Строка `exit-ip` называет ответивший сервис.

Клиенты address service/resolver не наследуют `-k`, в том числе для HTTPS proxy.
Cookies целевого сайта им не передаются. Probe целевого origin использует
TLS policy этого origin. IP lookup остаётся диагностикой, его неудача не
срывает основной fetch.

## JSON и границы движка

Существующий JSON уже определяет site partitioning, лимиты пула, idle timers,
TLS resumption и протокольные параметры. A9 меняет владение клиентом внутри CLI
и явный выбор пользователем диагностических запросов. Новых browser values,
UA/name dispatch, profile primitives или fork API не добавлено.
Все 18 profile JSON и `engine/version.json` сохранены. Это тот же неопубликованный
engine 1.0.0/schema 4/daemon 3; нового major до публикации1.0.0 не требуется.

## Реальный Chrome

Chrome 156.0.8078.74, macOS 27.0.1 arm64; headed, свёрнутые фоновые окна,
CDP navigation, отдельный user-data-dir на запуск. Два независимых набора:
по 3 запуска на каждый из H1/H2 ×1/4 параллельных запросов; всего 24 запуска Chrome.
В каждом 8 GET к одному свежему локальному TLS origin, `no-store`, ответ 40 ms.
Chrome навигирует вкладки волнами; CLI использует 4 строки ×2 повтора.
Это сравнение соединений, не равенство navigation timing или заголовков.
Локальный сертификат принят явно обоими акторами; интернет/proxy не входят.

| Сценарий,8 запросов | Chrome,6 запусков | Исходный CLI | Итоговый CLI `1cc4f81` |
| --- | --- | --- | --- |
| H1, последовательно | 1 обслуживающее соединение | 8 | 1 |
| H1, 4 параллельно | 4 | 8 | 4 |
| H2, последовательно | 1 | 8 | 1 |
| H2, 4 параллельно | 1 | 8 | 1 |

Первый проход включал 72 последовательности/576 запросов: по 192 на Chrome,
исходный и промежуточный исправленный CLI. После изменения HTML-отчёта
точный итоговый бинарник `1cc4f81` отдельно повторил 24 сценария/192 запроса.
Всего сохранено 96 последовательностей/768 целевых запросов.

**Дополнительные сокеты Chrome сохранены как различие:** при последовательных
H1/H2 принято 2 TCP-сокета, но запросы шли по 1; при параллельном H2 принято 4,
но запросы шли по 1. В сценарии с выдержкой 40 ms итоговый CLI открывает 1/1/4 соответственно
обслуживанию, без этих дополнительных холодных сокетов. Другой мгновенный
H1-сценарий в CI, описанный ниже, показал и у CLI дополнительные холодные dial;
правило «CLI никогда не открывает неиспользуемые сокеты» не установлено. C05 закрыт по критерию общего пула
запросов; равенство всех TCP connect attempts не заявляется.

48 крупнейших CLI pcapng первого прохода независимо декодированы TShark4.6.9:
ожидаемые 1/2/8 GET в снимке совпали. Удаление embedded TLS keys даёт 0 GET вместо 8.
Ещё 24 снимка точного финального бинарника прошли тот же независимый декодер
и отдельный key-removal control.
PCAP содержит синтетические TCP/IP envelopes; это не измерение kernel packets.
Порты, времена, неиспользуемые сокеты и исходные значения не выкинуты.
Объединение результатов выполняется только по actor/origin/serving connection.
Снимок общего соединения содержит предыдущие байты до момента сохранения,
возможно байты других concurrent requests, но не будущий close.

## Нативный CI: уточнение фикстуры параллельного H1

Исходный запуск 41027356012 сохранил отказ `h1/4/shared`:5 принятых и закрытых
сокетов, но все 8 запросов прошли по 1. Мгновенные ответы позволяли готовому
соединению обслужить очередь до завершения остальных холодных dial. Предел
в 4 cumulative accepts без фактического overlap был неверной предпосылкой теста.

Тестовая коррекция удерживает первую четвёрку запросов до прихода всех четырёх.

все 8 запросов получены, все сокеты закрыты. При восстановлении старого
private-worker default этот сценарий и H2 по-прежнему отвергают движок.
