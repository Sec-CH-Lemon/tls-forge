## Исполнение профиля

`Profile.Validate` — общая проверка совместимости, полей и транспортной
семантики. JSON scanner до декодирования отказывает на неоднозначных ключах
(включая Go-эквивалентные Unicode/case варианты), null/нецелых/неверно типизированных
числах и выходе за разрядность. Ошибка содержит имя профиля, путь и ограничение.
Inspect остаётся offline; Save/Clone не легализуют архив. Parser ClientHello
по-прежнему проверяет его в Spec до транспортного I/O.

| Вход | Контроль |
| --- | --- |
| Load, файл/локальная директория, embedded registry | Общий validator; отсутствие fallback после ошибки выбранного профиля |
| Register/Get, возвращённые копии | Проверка и независимые snapshots; повреждённая сохранённая запись отвергается повторно |
| Catalogue template и adapter | Проверка исходного JSON до map/подстановки имени; разрешён только явно закреплённый preset |
| Spec/ClientProfile/Shuffled | Общая семантика до построения транспорта/hello |
| New/WithProfileValue, Fresh, Do | Отказ до resolver/transport/site/proxy activity |
| CLI pool, daemon, Node/Python | Реальный исполняемый путь через те же constructors; собственные origin/proxy counters |
| Raw transport override | Прежний обязательный запрет unversioned preset остаётся |

Прямые, HTTP/HTTPS/SOCKS5 proxy, custom TCP dial и QUIC racing пути проверяются
для7 неверных вариантов ×4 входов ×6 маршрутов =168 случаев. Считаются реальные
DNS queries, TCP accepts, TLS ClientHello, proxy/origin обращения, UDP datagrams
и вызовы backend constructor/wrapper. У отказов все равны0; положительные
контроли подтверждают наблюдатели. UDP socket syscall не перехватывается отдельно:
отсутствие UDP dials следует из раннего отказа до любого backend construction,
а на peer непосредственно измеряется отсутствие datagrams. Это явно ограниченная
проекция, не трасса всех системных вызовов процесса.

Допустимость HTTP2 определяется [RFC9113](https://www.rfc-editor.org/rfc/rfc9113.html),
boolean extensions — также [RFC8441](https://www.rfc-editor.org/rfc/rfc8441.html)
и [RFC9218](https://www.rfc-editor.org/rfc/rfc9218.html). INITIAL_WINDOW_SIZE0
допустим; MAX_FRAME_SIZE16384..16777215; клиентские stream IDs — odd31-bit.
Нулевой initial stream marker означает1. Проверяются зависимости, в том числе
фиксированная ссылка на будущий собственный поток, которая стала бы self-dependency.
Начальное SETTINGS ограничено одним16384-byte frame;2730 записей помещаются.
Повторные IDs не объявлены нарушением RFC: map-adapter явно отказывает на их
неподдержанном последовательном представлении, не схлопывая массив.

## HTTP2: контрпримеры и исправления

- До: id5/value1 реально отправлялся как `000500000001`; id4/value2147483648
  отказывал только после TCP/TLS. После: ошибка конструктора до I/O.
- До: объявленный stream window0 учитывался как65535; последний допустимый
  клиентский stream ID считался недоступным; переполнение connection increment
  могло отправить preface до отказа. После — точный0, последний31-bit ID и ранний
  bounds check.
- До: `connection_flow:0` подменялся15663105. Новый признак presence проходит
  Profile → tls-client → fhttp, включая Clone/configure и внешний H2 proxy.
  Теперь0 означает отсутствие WINDOW_UPDATE; предел2147418112 не переполняет
  начальные65535. Raw legacy backend default сохраняется только при отсутствии
  явного значения. Browser choices остаются в существующем JSON.
- Независимый raw H2 peer читает исходные binary frames, не используя framer
  кандидата. Проверяются порядок/значения, min/max, пустой SETTINGS,2730 записей,
  нулевой/единичный/максимальный increment, последний клиентский stream ID.
- Дополнительный production oracle выявил висящий body reader: DATA с END_STREAM
  удалял stream из map до обнаружения flow error. Ошибка теперь доставляется
  также этому reader. Проверены terminal/nonterminal ×window0/1; исходный
  зависший контрпример и goroutine dump сохранены.

## HTTP3: большой начальный control stream

До: валидные GREASE payload1452/4096 и260 SETTINGS могли блокировать QUIC run loop,
request cancellation и Close. Синхронная запись теперь ограничена внутренним
packet buffer; остаток пишет setup goroutine. Малый префикс сохраняет композицию
with-finished. Request streams ждут завершения local setup, не peer SETTINGS/ACK.
Проверены реальный Client.Do, finite response, cancellation при peer stream
window32 и bounded Close. Это generic I/O/state primitive; новые JSON defaults,
browser dispatch и новый major не вводились.

## Форки и F09/этап1

[Поимённый реестр](../../../verification/fork-failures.json) сохраняет причины,
классы, обязательства, минимальные команды и хэши baseline. Каждый из четырёх
форков запускается полностью на standalone graph и на версиях, реально
линкуемых production CLI/библиотекой; полные module graphs сохранены отдельно.
Все прогоны используют Go1.26.10, GOWORK=off, без локальных replace в продукте.
Корневой fhttp идёт отдельно; между его запусками не менее45с. Единственный
skip — TestOmitHTTP2 по owner LEMON.md; его замещающее обязательство остаётся A11.

QUIC self integration реально собирается и выполняется. Test-only adapter читает
фактически согласованную группу из uTLS connection state и падает при исчезновении
witness; фиктивная группа не возвращается. Это handshake-state witness, не новый
независимый криптографический wire oracle. Старые групповые assertions сохранены.

В full-suite sandbox разрешён только loopback. Внешние DNS fixtures и sendfile,
который эта политика запрещает также на loopback, остаются поимёнными средовыми
отказами с воспроизведением на неизменённых исходниках. Их сетевые обязательства
не считаются исполненными. Внешний TestWeb не может отправить POST. Гейт отказывает
на неизвестном падении, несовпадении диагностического семейства, build failure,
panic/timeout/race, неполном наборе или незапущенном self. CI настроен на
main/development с отменой устаревшего прогона и сохранением raw artifacts.

В локальной приёмке восемь гейтов имеют `accepted:true`, а не восемь зелёных fork
suites. F09/этап2 остаётся открытым, в том числе serializer/response metadata,
Clone, retry/cookie contracts, ошибочные/внешние fixtures и прежние race-only
QUIC allocation/simnet проблемы. Конфигурация CI и локальный прогон не являются
доказательством удалённой активации: fork commits/pins ещё не опубликованы.

## Границы доказательств

- Нового Chrome actor нет. Эти source/owned-peer проверки не доказывают браузерную
  неотличимость, Chrome timing/distributions, WAN или исторические Chrome/platform profiles.
- F01 реализован и локально принят в описанном объёме. F09/этап1 имеет локальный
  gate и CI-конфигурацию; его удалённая активация ещё не подтверждена. Этап2 и A7
  остаются открыты. Общая полнота JSON ownership F03 не закрывается A6: например,
  отсутствие header_priority использует прежний raw-backend fallback; явный
  нулевой объект уже позволяет выбрать отсутствие legacy priority. Browser
  значения для такого отдельного изменения здесь не выбирались.
- Новые pins доступны в сохранённом local module proxy; push, публикация,
  SumDB-доступность и удалённый запуск CI не заявлены.
- Shared KB дополняется observation для PROFILE-006, HTTP3-008, REVIEW-004 и PROFILE-007;
  прежние browser target и historical observations сохраняются.
- Посторонние untracked файлы, owner go.work/tmp и staged backlog соседнего
  проекта не включаются в коммиты. Локальная заметка AGENTS.md обновлена;
